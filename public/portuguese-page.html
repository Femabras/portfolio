Estudo de caso

Femabrás

Uma plataforma web pensada primeiro em português para o dia-a-dia em Angola. Já em produção: dicas de futebol, quatro jogos no navegador, incluindo xadrez em tempo real, um painel para tipsters parceiros e uma consola de administração. Construído e em pré-lançamento: um localizador de ATM com mapa próprio, o primeiro passo para as pessoas indicarem que caixas perto delas têm dinheiro.

Destaques

  • Em produção

    Xadrez online em tempo real

    Com um link de convite, dois amigos jogam no navegador. Os Server-Sent Events levam cada mudança de estado aos dois jogadores e a quem estiver a assistir, e um motor no servidor é a única fonte de verdade: o cliente envia apenas a jogada, e o servidor valida-a, aplica-a e difunde a nova posição. A jogada de cada um aparece de imediato e é revertida se o servidor a rejeitar.

    • React
    • chess.js
    • SSE
    • Go
    • notnil/chess
  • Em produção

    Um motor de previsões que presta contas ao backtest

    Um modelo de Poisson em Go, com a força das equipas nas ligas e ratings Elo nos torneios, calcula resultados, totais de golos e ambas marcam. Um backtest avalia palpites passados com o próprio código de produção. Os palpites múltiplos de liga acertaram 39–45% contra 55–67% previstos, por isso foram desligados; os de torneio acertaram 59,8% contra 56,7% e ficaram.

A produção promove exactamente a imagem aprovada nesse ambiente, por um botão ou por uma tag de versão, e a integração contínua recusa uma tag sem entrada no registo de alterações.

  • Pré-lançamento

    Um mapa sem factura de mapas

    O localizador de ATM desenha com MapLibre GL a partir de um mapa vectorial só de Angola, alojado por mim: um arquivo PMTiles de 210 MB no Cloudflare R2, lido por pedidos HTTP parciais, sem nenhuma API comercial de mapas para pagar ou de que depender. A localização do visitante é arredondada para cerca de 1 km antes de ser enviada, e nunca é guardada.

  • Pré-lançamento

    Sessões que não caem

    Os tokens de acesso duram 15 minutos. O proxy do Next.js renova-os antes de expirarem e faz a rotação do refresh token, com uma janela de tolerância de 30 segundos para pedidos já em curso. O cliente partilha uma única renovação entre chamadas simultâneas e repete uma chamada rejeitada uma vez, mas nunca nos endpoints de autenticação nem na área de parceiros, onde o início de sessão bloqueia após falhas repetidas e uma repetição contaria como mais uma falha.

Notas de depuração

O botão de início de sessão que só falhava na primeira visita

Sintoma
O início de sessão com Google falhava para uns visitantes e funcionava para outros. O registo de produção mostrava os dois resultados na mesma hora.
O que o tornou difícil
Funcionava sempre que se chegava a /login navegando pelo site. Só falhava quando /login ou /register era a primeira página carregada, que é exactamente o caminho que os testes feitos de dentro da aplicação nunca percorrem.
Causa
O link vinha de uma função que escolhe a origem da API verificando typeof window. Isso responde a onde o código está a correr, que é a pergunta certa para fetch e a errada para um href. No primeiro carregamento, renderizado no servidor, o nome interno do contentor Docker ficava escrito na página, e nenhum navegador o consegue alcançar. O URL também não tinha o prefixo /api com que o cliente OAuth está registado.
Correcção
Uma origem pública da API para tudo o que o navegador resolve, usada pelos dois links. As 34 chamadas a fetch mantêm a função de modo duplo, que agora tem um comentário a indicar onde nunca deve aparecer.

O que aprendi: perguntar onde um URL vai ser resolvido, e não onde corre o código que o constrói.

Processo

Como trabalho

Os mesmos hábitos em cada alteração, seja uma correcção de uma linha ou uma nova área do produto.

  1. Decidir antes de construir

    Cada escolha importante torna-se um registo de decisão de arquitectura, com as opções, os seus prós e contras e uma recomendação, escrito antes do código. A Femabrás tem mais de 50.

  2. Uma só verificação, local e na integração contínua

    gofmt, go vet, testes Go e govulncheck, depois a verificação de i18n, os testes do frontend, lint e um build de produção, do mais rápido para o mais lento, para que uma falha apareça em segundos.

  3. Corrigir a causa

    Uma correcção nomeia a causa real. Se a correcção verdadeira estiver fora do âmbito, fica escrita, em vez de escondida atrás de um remendo.

  4. Com apoio de IA, sob a minha responsabilidade

    Escrevo a especificação e o ADR, o Claude Code implementa em modo de planeamento, e reviso cada diff antes do commit. A documentação segue no mesmo commit que a alteração.

Como a Femabrás se organiza

  1. Edge

    Cloudflare para DNS, proxy e TLS, com o R2 a guardar imagens, tiles do mapa e áudio privado

  2. Web

    Caddy à frente do Next.js 16 (App Router, renderização no servidor, next-intl, proxy de sessão), React 19, TypeScript e Tailwind CSS 4

  3. API

    Go com Gin: uma API REST com sessões JWT, limites de pedidos por rota e Server-Sent Events para jogos ao vivo, além de tarefas em segundo plano com Asynq

  4. Dados

    PostgreSQL através do GORM, e Redis para filas, limites de pedidos e estado de curta duração

  5. Entrega

    GitHub Actions para o GHCR, depois o ambiente de testes, depois a produção na Hetzner com Docker Compose; cópias de segurança com restic no Backblaze B2
